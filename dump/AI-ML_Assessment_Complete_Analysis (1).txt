--------------------------------------------------------------
1. WHAT IS THIS ASSESSMENT ABOUT?
--------------------------------------------------------------

The assessment asks you to build a small AI system that performs RESUME INTELLIGENCE / RESUME PARSING.

In simple words:

INPUT:
A resume, usually represented as text.

OUTPUT:
Structured information, typically JSON.

Example input:

John Doe
MSc Computer Science
ABC University
Python, Java, SQL

Example output:

{
  "name": "John Doe",
  "education": [
    {
      "degree": "MSc Computer Science",
      "institution": "ABC University"
    }
  ],
  "skills": [
    "Python",
    "Java",
    "SQL"
  ]
}

However, the assessment is NOT merely asking you to create an API that calls an existing OpenAI/Gemini model.

Its stated objective is to demonstrate that you understand how to BUILD/ADAPT a DOMAIN-SPECIFIC LLM rather than simply consuming hosted APIs.

The assessment therefore covers the complete lifecycle:

1. Choose an appropriate open-source model.
2. Create a domain-specific instruction-tuning dataset.
3. Fine-tune/adapt the model or design the complete training pipeline.
4. Build a rigorous evaluation methodology.
5. Build a small usable inference script/API.
6. Package everything into a clean GitHub repository.

The assessment has five parts:

Part 1 — Research & Model Selection: 20 marks
Part 2 — Dataset Creation: 25 marks
Part 3 — Fine-Tuning / Adaptation: 25 marks
Part 4 — Evaluation Framework: 20 marks
Part 5 — Engineering: 10 marks

TOTAL = 100 marks

The biggest areas are DATASET + TRAINING = 50 marks.

B. WHY THIS MODEL?

Explain why the selected model fits resume parsing.

Resume parsing requires:

- Understanding semi-structured text
- Extracting entities

- Producing consistent JSON
- Handling missing fields
- Handling noisy resume formats
- Running at reasonable cost

- 0.5B
- 1B

- 3B
- etc.

Discuss hardware required for:

1. Inference

For example:

Inference:

Training:
- GPU with sufficient VRAM

You should explain the expected compute requirements rather than simply saying "GPU required."

E. CONTEXT WINDOW

Explain how much input text the model can process.

This matters because resumes can be long.

You should consider whether the model's context window is sufficient for realistic resumes.

F. LICENSE

Discuss whether the model can be used for the intended application and mention any important restrictions.

G. PROS & CONS

Do not write shallow points such as "fast" or "good."

Discuss meaningful engineering trade-offs such as:

- Model size
- Speed
- Memory requirements
- Fine-tuning difficulty
- Instruction following
- Structured JSON generation
- Accuracy
- Deployment complexity

H. WHY NOT ANOTHER POPULAR MODEL?

Example:

- More expensive

Model B:

5. WHAT MAKES THE DATASET "HIGH QUALITY"?
--------------------------------------------------------------

The assessment explicitly says that dataset QUALITY is more important than quantity.

Do not create 50 examples where only the candidate name changes.

The dataset should cover:

A. DIVERSE RESUME FORMATS

Examples:

- Traditional text resume
- Two-column resume converted to text
- Resume with tables
- Bullet-point resume
- Different section ordering
- Different wording for sections

B. MISSING FIELDS

Examples:

- No phone number
- No email
- No education
- No experience
- No certifications

The model should NOT invent missing information.

For example:

{
  "phone": null

C. VARYING LAYOUTS

Different resumes may use:

- EDUCATION
- Academic Background
- Education & Qualifications

or:

- EXPERIENCE
- Professional Experience
- Employment History

The model should understand the semantic meaning despite wording differences.

D. EDGE CASES

Useful edge cases include:

- Missing email
- Multiple phone numbers
- Multiple degrees
- No professional experience

- Multiple simultaneous roles
- Skills embedded inside project descriptions
- Unusual job titles
- Certifications
- Foreign/alternative date formats
- Inconsistent dates
- Empty sections
- Duplicate information
- Skills appearing in different sections

--------------------------------------------------------------
8. WHAT IS LoRA?
--------------------------------------------------------------

Normal fine-tuning tries to update a very large number of model parameters.

Conceptually:

Original large model
       |
       v
Update many weights
       |
       v
High compute/memory cost

LoRA takes a more efficient approach.

Conceptually:

Original model
       |
       +--> Keep original weights mostly frozen
       |
       +--> Train small additional adapter matrices

This greatly reduces the number of trainable parameters.

The assessment specifically suggests LoRA/QLoRA because these approaches make small-model adaptation more practical.

--------------------------------------------------------------
9. WHAT IS QLoRA?
--------------------------------------------------------------

QLoRA combines:

Quantization
+
LoRA

The base model can be loaded using lower-precision/quantized weights, while LoRA adapters are trained.

Conceptually:

Normal fine-tuning
-> high memory requirement

LoRA
-> fewer trainable parameters

QLoRA
-> quantized base model + LoRA adapters
-> lower memory requirement

14. HOW TO MEASURE PARSING ACCURACY
--------------------------------------------------------------

Compare:

GROUND TRUTH
versus
MODEL PREDICTION

Field by field.

Possible comparison:

- Name -> exact match
- Email -> exact match
- Phone -> exact match
- Skills -> set precision/recall/F1
- Education -> structured comparison
- Experience -> structured comparison
- Certifications -> structured comparison

This is stronger than subjective manual inspection.

--------------------------------------------------------------
15. HOW TO DETECT HALLUCINATIONS
--------------------------------------------------------------

A hallucination occurs when the model generates information not supported by the resume.

Example resume:

Python, SQL

Model output:

Python, SQL, TensorFlow, AWS, Docker

If TensorFlow/AWS/Docker were not supported by the resume, they are unsupported extractions/hallucinations.

You can measure an:

Unsupported-field rate
or
Hallucination rate

The evaluation should check whether extracted information is supported by the source resume.

--------------------------------------------------------------

--------------------------------------------------------------

The assessment explicitly asks for JSON validation.

A model may output:

"Here is your result:

{
  "name": "John",

In your system, validate the generated output.

For example, conceptually:

json.loads(output)

Then classify:

- Valid JSON
- Invalid JSON

A useful metric:

JSON validity rate

Example:

48 valid outputs / 50 total
= 96% JSON validity

--------------------------------------------------------------
17. HOW TO COMPARE TWO MODEL VERSIONS
--------------------------------------------------------------

Suppose:

Model v1
versus
Model v2

Run both on the SAME evaluation set.

Example:

Metric                v1       v2
-----------------------------------
JSON validity         90%      98%
Field F1              82%      89%
Hallucination rate     8%       3%

This lets you make an objective comparison.

Do NOT compare two models on different test sets.

--------------------------------------------------------------
18. REGRESSION TESTING
--------------------------------------------------------------

Regression testing means checking that improvements in one area did not break something that previously worked.

Example:

Old model correctly handles:

Resume with no phone number

After retraining:

New model starts inventing phone numbers.

That is a regression.

Maintain a fixed test suite:

regression_tests/
    test_001.json
    test_002.json
    test_003.json
    ...

Every time you retrain:

New model
   |
   v
Run fixed regression tests
   |
   v
Compare results
   |
   v
Detect regressions

This is an important real-world ML engineering practice.

30. RECOMMENDED EXECUTION ORDER
--------------------------------------------------------------

Do NOT start by randomly coding the API.

Use this order:

STEP 1
Choose the exact model and overall architecture.

STEP 2
Define the output JSON schema.

STEP 3
Design the 50 high-quality examples.

STEP 4
Create train / validation / test splits.

STEP 5
Run the BASELINE model before fine-tuning.

STEP 6
Fine-tune using LoRA/QLoRA if possible.

STEP 7
Run the SAME evaluation set after fine-tuning.

STEP 8
Measure improvement objectively.

STEP 9
Build the inference script/API.

STEP 10
Package everything into GitHub + README + research document.

This order is important because:

Part 1 influences Part 3.
Part 2 directly influences Part 3.
Part 2 also determines how Part 4 can evaluate the model.
