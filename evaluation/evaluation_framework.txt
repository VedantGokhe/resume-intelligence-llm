2. ANSWERS TO ALL ASSESSMENT EVALUATION QUESTIONS (SIMPLE & DETAILED)
================================================================================

--------------------------------------------------------------------------------
Question 1: What metrics would you use?
--------------------------------------------------------------------------------
Answer (in simple words):
We use a 5-layer metrics suite so we do not rely on just one single score:

1. Lexical JSON Validity Rate (%): Measures if the output is valid JSON code that python 
   can parse with `json.loads()`.
2. Schema Adherence Rate (%): Measures if the output strictly uses our exact required 
   field names (`name`, `email`, `phone`, `skills`, `education`, `experience`, `projects`) 
   and correct data types.
3. Field Exact Match Accuracy (%): Measures exact matches for single fields like candidate 
   Name, Email, and Location.
4. Precision, Recall, and F1-Score (%): Measures list extraction quality for skills, 
   certifications, and links.
5. Hallucination Rate (%): Measures whether extracted information was invented by the model 
   or actually exists in the original resume text.
6. Novel Semantic Distance (Embedding Similarity): Uses sentence-transformers 
   (`all-MiniLM-L6-v2`) to measure semantic similarity for long text summaries.


--------------------------------------------------------------------------------
Question 2: How would you measure parsing accuracy?
--------------------------------------------------------------------------------
Answer (in simple words):
Different resume fields require different evaluation math:

a) Scalar Fields (Name, Email, Location):
   We normalize strings (lowercase, strip whitespace) and calculate exact match accuracy:
   Match = 1 if Predicted == Target else 0.

b) List Fields (Skills, Certifications, Links):
   We treat extracted skills as a set of items and calculate Precision, Recall, and F1:
   - Precision = (Correct Extracted Skills) / (Total Extracted Skills)
   - Recall    = (Correct Extracted Skills) / (Total Actual Skills in Resume)
   - F1-Score  = 2 * (Precision * Recall) / (Precision + Recall)

c) Structured Sub-Objects (Education, Experience, Projects):
   We match nested attributes pairwise (e.g., verifying `degree` matches degree and 
   `institution` matches institution).


--------------------------------------------------------------------------------
Question 3: How would you detect hallucinations?
--------------------------------------------------------------------------------
Answer (in simple words):
A hallucination occurs when the AI invents information (like adding "AWS" to skills when 
the candidate never mentioned AWS in their resume).

Our automated hallucination detector works via Source Text Containment Verification:
1. Every extracted text token (name, company, skill) is lowercased.
2. The code checks if that exact text string exists anywhere inside the original raw resume text.
3. If an extracted item is NOT found in the original resume text, it is flagged as a hallucination.
4. Hallucination Rate = (Unsupported Items / Total Extracted Items) * 100.

Our fine-tuned model achieved a 3.75% hallucination rate, well below our safety threshold of < 5.0%.


--------------------------------------------------------------------------------
Question 4: How would you validate JSON correctness?
--------------------------------------------------------------------------------
Answer (in simple words):
We use a 2-stage verification pipeline:

Stage 1 — Lexical Check (`json.loads`):
  We strip any markdown wrappers (like ```json ... ```) and check if the string can be 
  parsed into a Python dictionary.

Stage 2 — Semantic Schema Check (`Pydantic`):
  We pass the dictionary into `ResumeSchema.model_validate(json_dict)`. This ensures:
  - Required field names are present (e.g., `skills`, not `"competencies"`).
  - Field data types match (e.g., `phone` must be a List `[]`, not a single string `""`).
  - Missing scalar fields are `null` and missing list fields are `[]`.


--------------------------------------------------------------------------------
Question 5: How would you compare two model versions?
--------------------------------------------------------------------------------
Answer (in simple words):
We run our automated evaluator script `evaluation/evaluate.py` across a fixed test set 
(`data/test.json` - 15 examples).

The script outputs a side-by-side JSON comparison report (`report.json`) tracking delta 
improvements in:
- Schema Validity Rate (0% -> 100%)
- Name & Email Accuracy (50% -> 100%)
- Skills F1 Score (30% -> 74.44%)
- Hallucination Rate (0% -> 3.75%)


--------------------------------------------------------------------------------
Question 6: How would you perform regression testing after retraining?
--------------------------------------------------------------------------------
Answer (in simple words):
Whenever we retrain the model on new data, we run an automated Regression Test Suite 
(`evaluation/regression_tests.py`) covering 4 critical real-world edge cases to ensure 
the model hasn't forgotten rules (catastrophic forgetting):

- REG-01 (No Phone Number)  : Verify `phone` output is empty list `[]`.
- REG-02 (No Email Address) : Verify `email` output is `null`.
- REG-03 (Fresh Graduate)   : Verify `experience` output is empty list `[]` without fake jobs.
- REG-04 (Multiple Phones)  : Verify all phone numbers are captured in `phone` list.

Our fine-tuned model passed 4/4 (100%) regression tests.

3. DEEP ANALYSIS OF BEFORE VS. AFTER FINE-TUNING RESULTS
================================================================================

Why did the Base Model fail on Name Accuracy (50%) and Schema Validity (50%)?
--------------------------------------------------------------------------------
1. Key Name Inconsistency:
   In Sample 4, the base model outputted `"candidate_name": "Rohan Kulkarni"` instead of `"name"`.
   In Sample 6, the base model outputted `"candidate_name": "KARTIK VARMA"` instead of `"name"`.
   Because the schema expected `"name"`, Pydantic failed to find the field -> 50% penalty.

2. Casing Inconsistency:
   In Samples 1 & 2, the base model extracted ALL-CAPS names (`"ARJUN MEHRA"`, `"RAHUL KRISHNAMURTHY"`), 
   whereas ground truth targets clean Title Case (`"Arjun Mehra"`).

3. Thinking Tag Injection (`<think></think>`):
   The base Qwen3 model is a reasoning model that outputs internal `<think>` scratchpads by default.
   Fine-tuning completely eliminated these tags, producing clean JSON immediately.

4. Data Type Mismatches:
   In Sample 2, the base model returned `education` as a single dictionary `{}` instead of a list `[]`.
   Fine-tuning fixed all data types to strictly conform to lists `[]`.
